Tool Recommendation lets an agent describe a task and get back only the tools that fit it, instead of holding every tool on a gateway in its context. This page is for agent developers and platform operators who run gateways with many tools. It explains what an MCP client gets when Tool Recommendation is on, how the agent finds and calls tools, and what decides the quality of the results. Read it before you [turn Tool Recommendation on](/en/operate/governance/mcp-gateways/tool-recommendation/configure) for a gateway.

## Why it exists

An MCP client normally lists every tool on a gateway and passes all of their names, descriptions, and input schemas to the model. A gateway that federates a handful of MCP servers can expose hundreds of tools. At that size the tool definitions consume a large share of the context window, and the model picks the wrong tool more often because it has too many near-matches to choose from.

With Tool Recommendation on, the gateway lists a small, fixed set of Arcade tools. The agent asks for the tools it needs when it needs them, and Arcade returns the few that match.

## What an MCP client gets

When Tool Recommendation is on for a gateway, the gateway's tool list contains these Arcade tools instead of the allowed tools:

| Tool | What it does |
| --- | --- |
| `Arcade.SelectTools` | Takes one or more task descriptions and returns the tools that match each task most closely, with their full input schemas. |
| `Arcade.UseTool` | Runs a tool by name with the inputs you pass. |

The MCP tool list spells these names with an underscore separator, for example `Arcade_SelectTools`. Arcade accepts either form in a tool call.

## How an agent finds and calls a tool

The agent works in two steps.

First, it calls `Arcade.SelectTools` with the tasks it wants to complete. Each entry in `tasks` describes one separate action:

```json
{
  "tasks": ["send a Slack message to a channel", "create a GitHub issue"],
  "context": "The user is triaging a production incident"
}
```

Arcade returns up to five tools per task, ranked by how well they match. Each result includes the tool's name, description, and input schema, plus a `query_id` for the whole request.

When a task gets no tools, its result includes an `empty_reason`. The agent uses it to decide whether to retry:

- `no_match`: Arcade finished the lookup and found no tool the agent may use for that task. Retrying the same task returns the same answer.
- `unavailable`: The lookup for that task didn't complete. Retrying may succeed.

Second, the agent calls `Arcade.UseTool` with the tool it picked and that tool's own arguments nested inside `inputs`:

```json
{
  "tool_name": "Slack.SendMessage",
  "inputs": {
    "channel_name": "incidents",
    "message": "Investigating elevated error rates on checkout."
  },
  "query_id": "the query_id returned by Arcade.SelectTools"
}
```

`query_id` is optional. Arcade uses it to connect the tool execution to the recommendation that surfaced it.

The tool descriptions that Arcade serves tell the model how to use this flow, so most agents need no extra prompting.

## How selection works

`Arcade.SelectTools` matches each task against the tools the gateway allows, using both the words in the task and its meaning, and returns the closest matches first. Matching on meaning finds a tool even when the task shares no words with it, for example "let the team know the deploy finished" matching a Slack tool. The optional `context` helps Arcade rank the matches.

## What Arcade can recommend

Tool Recommendation doesn't change which tools an agent can use. `Arcade.SelectTools` returns only tools that the gateway allows, and `Arcade.UseTool` runs any tool that the gateway allows, whether or not `Arcade.SelectTools` returned it.

Policy enforcement and authorization work the same way with Tool Recommendation on or off. See [Contextual Access](/en/operate/governance/contextual-access) for how access rules decide which tools each user can see and use, and [Authorized Tool Calling](/en/build/tool-calling/custom-apps/auth-tool-calling) for how tools run as the end user.

## Use it over the REST API

Agents and apps that don't connect through MCP can call the same operations as REST endpoints of the [Arcade API](/en/references/api):

| Endpoint | MCP tool | What it does |
| --- | --- | --- |
| `POST /v1/tools/select` | `Arcade.SelectTools` | Returns the tools that match each task. |
| `POST /v1/tools/search` | None | Ranks tools by how well their words match a keyword query. |
| `POST /v1/tools/execute` | `Arcade.UseTool` | Runs a tool by name. |
| `GET /v1/apps` | `Arcade.ListApps` | Lists the apps the user can act on, and whether each is connected. |

Authenticate with your Arcade API key as a bearer token. With an API key, name the end user Arcade acts for in `user_id`. These endpoints don't read a gateway's Tool Recommendation setting. If Tool Recommendation isn't available in your deployment, `select` and `search` return `503`.

### Select tools

```bash
curl -X POST "https://api.arcade.dev/v1/tools/select" \
  -H "Authorization: Bearer $ARCADE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "tasks": ["send a Slack message to a channel", "create a GitHub issue"],
    "context": "The user is triaging a production incident",
    "user_id": "{user_id}",
    "gateway_id": "{gateway_id}",
    "top_k": 3
  }'
```

- `tasks` is required. Each task gets one entry in `results`, in the order you sent them.
- `top_k` sets the number of tools per task. It defaults to 5, and values above 20 return 20.
- `gateway_id` is optional. With it, Arcade considers only the tools that gateway allows. Without it, Arcade considers every tool the user can access in the project.

```json
{
  "query_id": "8b0f6a52-3c1e-4d4e-9a57-2f1c0e6d9b21",
  "results": [
    {
      "task": "send a Slack message to a channel",
      "suggestions": [
        {
          "tool_name": "Slack.SendMessage",
          "description": "Send a message to a Slack channel or user.",
          "input_schema": {
            "type": "object",
            "properties": {
              "channel_name": { "type": "string" },
              "message": { "type": "string" }
            }
          }
        }
      ]
    },
    {
      "task": "create a GitHub issue",
      "suggestions": []
    }
  ]
}
```

An empty `suggestions` list means no tool the user may use matched that task. If the lookup fails for any task, the whole request fails: `503` means the service is temporarily unavailable and a retry may succeed.

### Search tools

`POST /v1/tools/search` takes a `query` and returns `results`, a list of tools in the same shape as `suggestions`, ranked by keyword match. `top_k` defaults to 10, and values above 50 return 50. It accepts the same `user_id` and `gateway_id` as `select`.

### Run a tool

`POST /v1/tools/execute` runs a tool by `tool_name` with its arguments in `input`. Pass the `query_id` from `select` to connect the execution to the recommendation that surfaced it:

```json
{
  "tool_name": "Slack.SendMessage",
  "input": {
    "channel_name": "incidents",
    "message": "Investigating elevated error rates on checkout."
  },
  "user_id": "{user_id}",
  "query_id": "8b0f6a52-3c1e-4d4e-9a57-2f1c0e6d9b21"
}
```

This endpoint doesn't take a gateway, so it isn't limited to what `select` returned or to one gateway's tools. It can run any tool in the project that the user can access, and your access rules apply to every call. See [Authorized Tool Calling](/en/build/tool-calling/custom-apps/auth-tool-calling) for what happens when a tool needs the user to authorize first.

### List apps

`GET /v1/apps?user_id={user_id}` returns one entry per app the user can act on through the project, sorted by `app_id`, with `limit` and `offset` for paging. `connected` is `true` when the user can call the app's tools without authorizing first. When it is, `account` and `permissions` show the account the user connected and the scopes that connection grants. It reports the same apps as `Arcade.ListApps`.

Errors from these endpoints use the Arcade API's error body, with a `name` such as `service_unavailable` and a `message`. A request that fails validation also lists `field_errors`.

## How it works with MCP clients

Tool Recommendation runs inside the gateway and speaks standard MCP. The Arcade tools are ordinary MCP tools, so any MCP client that can connect to an Arcade MCP Gateway can use them. You don't need an Arcade SDK, a client plugin, or code changes in your agent.

## What makes recommendations good

Arcade matches a task against each tool's name and description. The input parameters are not part of the match, and Arcade reads only the first line of each description.

That makes tool descriptions the main factor you control. A tool with a vague or empty first line is hard to recommend, however useful the tool is. When you [build your own tools](/en/build/create-tools) or register a [remote MCP server](/en/operate/governance/remote-mcp-servers):

- Start each description with one sentence that says what the tool does and to what, for example "Send a message to a Slack channel or user."
- Name the service or object the tool acts on. "Create an issue in a GitHub repository" matches more tasks than "Create an item."
- Give tools that do different jobs descriptions that read differently. Two tools whose first lines are nearly identical compete for the same tasks.
